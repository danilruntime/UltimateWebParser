# Парсер SoundCloud: треки из «trending» — дизайн

Дата: 2026-11-22
Статус: утверждена 2026-11-22

## 1. Зачем

Нужен второй парсер рядом со `steam_deals`, чтобы сервис не выглядел
одноцелевым: сайт SoundCloud, отчёт с треками из раздела «в тренде». Задача
продуктовая, не техническая: админ включает сайт в боте и получает `.ods` со
списком треков так же, как получает скидки Steam.

Решения, принятые до дизайна (в беседе): собираем **метаданные треков**, а не
аудиофайлы; источник — **trending по жанрам**; вход в аккаунт SoundCloud **не
обязателен** (анонимная страница отдаёт всё нужное).

## 2. Что должно получиться

- Новый парсер `soundcloud_trending` в `src/uwp/parsers/soundcloud_trending/`,
  обнаруживаемый реестром без правок в других местах.
- `url` = `https://soundcloud.com/discover` (то, что называет отчёт),
  `auth_url` = `https://soundcloud.com/signin` (форма входа для VNC),
  `requires_login = False`.
- Один прогон = один жанр: админ выбирает жанр в настройках сайта, парсер
  открывает соответствующую страницу `trending-by-genre:<жанр>` и отдаёт до 50
  строк — по строке на трек.
- В отчёте: название, исполнитель, ссылка на трек, ссылка на исполнителя, жанр,
  длительность, прослушивания, лайки, репосты, комментарии, дата публикации.
- Счётчики помечены `volatile=True`: они меняются сами, и режим
  `export_mode=changes` не должен из-за них присылать файл каждый прогон.
- Заголовки, название и описание парсера и подписи настроек — в каталоге
  `uwp.i18n.parsers` для `ru` и `en`; README парсера на двух языках.
- Пустая страница (геоблок, смена разметки, капча) — `ParseError(kind=blocked)`
  с сохранённым артефактом `empty.html`, а не пустой отчёт.
- Числа в отчёте **точные**, а не округлённые: прослушивания и лайки берутся из
  того же JSON, который страница получает для отрисовки, а не из текста строки.
  Если этот JSON не удалось получить ни перехватом, ни `fetch` — прогон падает
  `blocked`, а не пишет отчёт с приблизительными числами (обоснование —
  раздел 5).

## 3. Не-цели

- **Скачивание аудио.** Для этого нужен `transcodings` + `track_authorization`,
  а часть треков правообладатель не отдаёт вовсе. Отдельная задача, отдельный
  дизайн.
- **Свой аккаунт**: лента `/stream`, лайки `/you/likes`, плейлисты пользователя.
  Требует живой сессии и делает отчёт персональным.
- **Чарты** (`music-charts-us/sets/all-music-genres`) как второй источник.
  Добавится настройкой, если понадобится; сейчас это лишняя развилка.
- **Сортировка и фильтры** (по прослушиваниям, по дате, «только новое за
  сутки»): порядок trending осмыслен сам по себе.
- **Настройка «сколько строк»**. Отчёт и так не больше 50 строк, а обрезка ломает
  учёт пропавших: при лимите 10 остальные 40 станут `absent`, а после возврата к
  полному списку — снова «новыми». Плейлист целиком и только он.
- **Подгрузка больше 50 треков**: страница отдаёт не больше 50, скролл добавляет
  только отрисовку, не новые записи.
- **Запасной разбор DOM**: отклонён как путь данных, доводы в разделе 5.
- **Засеянный сайт SoundCloud**: `seed.py` создаёт ровно один пример (Steam), и
  это поведение не меняется — второй выключенный сайт только засоряет первый
  экран. Админ добавляет SoundCloud сам.
- Миграции БД и новые зависимости. Уточнение: одна миграция появилась позже,
  при смене пина браузера — `007_browser_brand_version.sql` приводит
  `profiles.brand_version` сохранённых профилей к мажору установленной сборки, иначе
  User-Agent и `sec-ch-ua` называют разные Chrome (замерено). Новых зависимостей
  по-прежнему нет.

## 4. Ограничения (замерено)

Всё ниже измерено в контейнере `uwp-worker` на живой странице
`https://soundcloud.com/discover/sets/trending-by-genre:all-genres`; первый пункт —
повторной проверкой уже собранного алгоритма (hydration + перехват):

- **Проверенный алгоритм работает без скролла.** `domcontentloaded` → hydration
  уже есть (50 id), перехват `/tracks` покрыл все 50 за 1,5 с.
- **Страница отдаёт 50 треков, но в DOM сначала 10.** Бесконечный скролл
  доводит список до 50 (`mouse.wheel` × 3–4). Без скролла DOM неполный, поэтому
  DOM не может быть источником полного списка «как есть».
- **Полные объекты треков приходят одним запросом самой страницы**:
  `api-v2.soundcloud.com/tracks?ids=<50 id>&client_id=…` → 200, 50 объектов,
  ~200 КБ. Запрос уходит при загрузке, до скролла.
- **`window.__sc_hydration` содержит `systemPlaylist`**: название плейлиста и
  `tracks` — до 50 записей вида `{id, kind, monetization_model, policy}`, только
  идентификаторы. Блок есть и в HTML, снятом обычным `curl` (88 КБ), то есть
  сервер его рендерит.
- **Порядок hydration совпадает с порядком DOM** (проверено на 50 строках), а
  **порядок в ответе `/tracks` — нет**: API возвращает объекты в другом
  порядке, поэтому строки надо раскладывать по id из hydration, а не по
  порядку ответа.
- **`apiClient` в hydration** содержит `id` (client_id) и `isExpiring`; запрос
  `fetch` из страницы с этим id отдаёт те же 200 и те же объекты.
- **Жанры на `/discover`**: `all-genres`, `trap`, `hip-hop`, `pop`,
  `electronic`. Слаги важны: `hip-hop-rap` даёт 404, `hip-hop` — 200;
  `electronic` — 200. Число треков не всегда 50: `hip-hop` отдал 49.
- **`li.systemPlaylistTrackList__item`** — контейнер строки; внутри
  `.trackItem__username` (текст и `href`), `.trackItem__trackTitle` (текст и
  `href` с `?in_system_playlist=…`), `.trackItem__playCount` (округлённо:
  `1.25M`, `411K`). Даты публикации в DOM нет.
- **Автор в DOM может быть списком** (`janecocaine, prodwhiteball`), а в API —
  один `user.username` (`ICEGERGERT` у первого трека другого прогона). DOM и
  API описывают один и тот же трек по-разному; источником истины остаётся API.
- **Анонимный доступ работает**: `requires_login = False` не мешает
  залогиниться вручную, если админ захочет (VNC открывает `/signin`).
- **fingerprint-chromium 150.0.7871.186 на этой странице иногда падает.** С
  `--fingerprint=<любой seed>` рендерер время от времени умирает
  (`Page.content: Target crashed`) уже после того, как серверный HTML пришёл, и
  до запроса `/tracks?`; в замерах ревью это 2 из 6 прогонов, в более ранних —
  1 из 10. Без флага страница живёт, остальные страницы SoundCloud живут и с
  флагом. Не помогают `--disable-gpu`, `--disable-webgl`, `--disable-3d-apis`,
  `--disable-gpu-compositing`, `--disable-spoofing`, headed-режим под Xvfb и
  ожидание. Сборка 148.0.7778.215 с теми же флагами страницу отрисовывает
  стабильно (3 из 3 в ревью, плюс контейнерные прогоны), hydration и `/tracks?`
  на месте — поэтому версия браузера закреплена на 148
  (`uwp.config.BROWSER_VERSION`). Это дефект сборки, а не парсера.

## 5. Подходы

**A. Только DOM.** Парсить `li` после прокрутки. Плюс: никакой зависимости от
внутреннего API. Минусы: числа округлены (`411K` вместо 411 037), даты
публикации нет, скролл нужно крутить до конца и ждать — хрупко и медленно.
Отвергнуто: теряет половину полезных колонок.

**B. Hydration-блок + перехват `api-v2` (выбран).** Порядок и состав берём из
`__sc_hydration[systemPlaylist]` (это id и название плейлиста, отрендеренные
сервером), точные значения — из ответа `/tracks`, который страница делает сама.
Своего client_id парсер не выдумывает и внутренние JS-бандлы не парсит.

**C. Только API по client_id, выдранному со страницы.** Быстро и без ожидания
загрузки, но `client_id` ротируется (`isExpiring`), а ошибка выглядит как
пустой отчёт. Отвергнуто как единственный путь; в B тот же приём используется
только как вторая попытка.

**Почему DOM не оставлен запасным путём.** Это изменение к первой редакции
дизайна, и оно осознанное — измеренное, а не вкусовое. `export_mode=changes`
сравнивает сохранённый payload с новым, а `items.upsert` перезаписывает payload
**всегда**, даже когда `runner` сохраняет строки с `complete=False`
(проверено на репозитории: после «частичного» прогона в базе лежит
приблизительное значение). У DOM-пути нет даты публикации, счётчики в нём
округлены, а автор показан списком, которого в API нет. Значит, его строки
затёрли бы точные значения предыдущего прогона, а когда API вернулся бы,
`changes` один раз соврал бы «изменилось». Если же SoundCloud сменит внутренний
API насовсем, отчёт навсегда останется приблизительным, и никто этого не
заметит.

Обходной путь — флаг «не сохранять строки» в `base.py`/`runner.py` — меняет
контракт парсеров ради одного парсера. Вторая попытка (тот же `/tracks` через
`fetch` из страницы) даёт ровно те же точные данные, поэтому честнее упасть
`blocked` с `empty.html`: админ и повтор получат шанс, а база не отравится.
Это решение владельца проекта (2026-11-22), а не вывод из кода.

## 6. Как это устроено

### URL и настройки

```python
TRENDING_URL = "https://soundcloud.com/discover/sets/trending-by-genre:{genre}"

class SoundcloudSettings(BaseModel):
    genre: Literal["all-genres", "pop", "hip-hop", "electronic", "trap"] = "all-genres"
```

`build_playlist_url(settings)` подставляет жанр. `url` парсера — константа
`https://soundcloud.com/discover`: отчёт называет раздел, а не конкретный жанр,
и эта ссылка не зависит от настроек (то же правило, что у Steam: `url` — это
`SEARCH_URL`, а параметры живут в `build_search_url`).

`genre` — `Literal`, потому что бот листает значения кнопкой; список взят из
ссылок самой страницы `/discover`, и выдуманный слаг (`hip-hop-rap`) даёт 404.
Новый жанр добавляется одной строкой, когда SoundCloud его опубликует.

### Прогон

1. Подписаться на ответы: `page.on("response", collector.handle)` — **до**
   `goto`. Обработчик читает тело только у URL с `/tracks` и `api-v2`, пока
   ответ ещё доступен, и складывает объекты в словарь `id → track`.
2. `page.goto(build_playlist_url(settings), wait_until="domcontentloaded")`.
3. `html = await page.content()`; `playlist = parse_hydration(html)` — название
   плейлиста, упорядоченные id и client_id. Никакого `page.evaluate` для чтения
   блока: он лежит в серверном HTML и доступен сразу, ещё до отрисовки строк.
4. Если блока нет или `ids` пуст → артефакт `empty.html` +
   `ParseError(kind=blocked, message="SoundCloud returned no playlist (geo block
   or markup change?)")`.
5. Если перехват ещё не покрыл все id — подождать до ~10 с короткими шагами,
   пока словарь не покроет `ids` или не истечёт таймаут. Скроллить не нужно:
   полнота берётся из hydration, а не из отрисовки.
6. Если после ожидания чего-то не хватает и `client_id` есть — один
   `page.evaluate` с
   `fetch("https://api-v2.soundcloud.com/tracks?ids=<недостающие>&client_id=<…>",
   {credentials: "include"})` из той же hydration-блоки. Так закрывается и
   «запрос ещё не пришёл», и «пришёл частично». Нет `client_id` — шаг
   пропускается, недостающие id остаются недостающими.
7. Собрать строки: идти по `ids` из hydration, брать объект из словаря. Если
   объектов нет **ни одного** → `ParseError(kind=blocked)` с `empty.html`.
   Объекты есть, но покрывают не все id → недостающие писать в `ctx.log`.
8. Объекты покрыли все id → `ParseResult(rows=..., meta={"playlist": title,
   "url": playlist_url, "objects": len(objects)})` — `meta` уходит в
   `RunOutcome` и в лог; в отчёт он не попадает (см. `report_meta`), поэтому
   «сколько пришло» читается в отчёте по строке «Строк».
9. Объекты покрыли часть id → та же логика, что на шаге 8, через
   `ParseError(kind=blocked, partial_rows=rows, message="SoundCloud returned N of
   M tracks")`: найденные строки сохраняются с `complete=False`, поэтому
   недостающие треки **не** помечаются `absent`, а следующий удачный прогон не
   превратит их в массу «новых». Пропуск — это неполный ответ API, а не пустой
   трек.

Порядок «hydration ids → объект» обязателен: иначе отчёт перемешивается при
каждом прогоне, а `changes` считает изменением порядок.

### Чистые функции (для юнит-тестов)

- `parse_hydration(html: str) -> Playlist | None` — разбирает
  `window.__sc_hydration = [...];`, находит `systemPlaylist` и `apiClient`,
  возвращает `title`, `ids`, `client_id`; на HTML без блока — `None`.
- `track_rows(ids, objects) -> list[dict]` — сборка строк, без браузера.
- `format_duration(ms: int | None) -> str` — `137331` → `2:17`; `None` → `""`.
- `published_date(value: str | None) -> str` — `"2026-11-12T21:17:35Z"` →
  `"2026-11-12"`; `None` → `""`.

### Строки и колонки

`external_key` — id трека строкой. Колонки:

| key | Заголовок | Источник API | `volatile` |
| --- | --- | --- | --- |
| `title` | Название | `title` | нет |
| `artist` | Исполнитель | `user.username` | нет |
| `url` | Ссылка | `permalink_url` | нет |
| `artist_url` | Исполнитель: ссылка | `user.permalink_url` | нет |
| `genre` | Жанр | `genre` | нет |
| `duration` | Длительность | `duration` (мс → `м:сс`) | нет |
| `published` | Дата публикации | `created_at` (дата, UTC) | нет |
| `playback_count` | Прослушивания | `playback_count` | **да** |
| `likes_count` | Лайки | `likes_count` | **да** |
| `reposts_count` | Репосты | `reposts_count` | **да** |
| `comment_count` | Комментарии | `comment_count` | **да** |

`url` и `artist_url` заканчиваются на `_url`, поэтому `ods` рисует их
гиперссылками. Пустое значение остаётся пустым (`None`), а не нулём: «нет
данных» и «ноль прослушиваний» — разные вещи, и волатильная колонка с нулём
давала бы ложное «изменение» при первом появлении числа.

`published` — текстом `YYYY-MM-DD` в UTC: `ods` не умеет формат даты, а
`report_meta` локализует только собственные даты. Пересчёт в часовой пояс
отчёта не делаем — сайт отдаёт момент публикации в UTC, и сдвиг на сутки в
колонке «дата публикации» был бы сюрпризом; сортировка по ISO-дате работает как
текст.

### Смена жанра у существующего сайта

`external_key` — id трека, поэтому после переключения `genre` все прежние
строки станут `absent`, а новые придут как «новые»: у сайта один набор
идентификаторов, и это ожидаемое поведение. Не-цель — «несколько жанров на
сайт»: такому админу нужен отдельный сайт на жанр. Пишем это в README парсера,
чтобы переключение не выглядело багом.

### Ошибки

- Нет `systemPlaylist` / пустые id → `blocked`, `empty.html` в артефакты.
  Причина на английском для лога: `"SoundCloud returned no playlist (geo block
  or markup change?)"`.
- Оба пути к `/tracks` не дали ни одного объекта → `blocked` с `empty.html`.
- Нет `apiClient` в hydration, но перехват всё покрыл — это не ошибка: строки
  полные, `fetch`-попытка не нужна. Нет `apiClient` и перехват неполный —
  недостающие id остаются недостающими, прогон `partial` по шагу 9. Отсутствие
  `client_id` само по себе не повод падать: без него теряются только строки,
  которых не было в перехвате.
- **Частичный ответ API — это `partial`, а не тихая потеря.** Найденные строки
  уходят в `ParseError(kind=blocked, partial_rows=rows)`; `runner` сохраняет их с
  `complete=False`, поэтому недостающие треки не помечаются `absent` и
  следующий полный прогон не выдаст их пачкой «новых». В чате прогон виден как
  частичный (`partial_head`).
- **Почему это не спасает от отравления базы, но здесь не мешает.** `upsert`
  перезаписывает payload и при `complete=False`, так что «частичный» отчёт
  сохраняет то, что в нём есть. Для SoundCloud это безопасно, потому что все
  сохранённые строки полные и точные: отсутствие строки означает «API не отдал
  объект», а не «данные хуже». Именно поэтому DOM-путь убран: он бы сохранял
  округлённые числа.
- `transient` не используем: сетевые сбои уже обрабатывает `runner`/`worker`
  через `page.goto`, а пустая страница — это `blocked`.

## 7. Проверка

Юнит-тесты (`tests/unit/test_soundcloud_parser.py`), фикстуры —
`tests/fixtures/soundcloud_playlist.html` (реальный серверный HTML, урезанный до
`<script>` с hydration-блоком: `systemPlaylist` и `apiClient`, данные не тронуты) и
`tests/fixtures/soundcloud_tracks.json` (5 реальных объектов, урезанных до нужных
полей):

- `parse_hydration` возвращает название плейлиста, id в порядке страницы и
  client_id; на HTML без блока — `None`.
- `track_rows` сохраняет порядок hydration, а не порядок ответа API (фикстура
  специально перемешана); пропускает отсутствующие id.
- `format_duration(137331) == "2:17"`, `published_date(...) == "2026-11-12"`.
- `run()` на фейковой странице: перехват сработал — строки точные; перехвата нет,
  `evaluate` вернул объекты — строки точные; ни одного объекта — `ParseError` +
  `empty.html`; объекты покрыли часть id — `ParseError` с `partial_rows`, и в
  нём ровно найденные треки.
- `build_playlist_url` для каждого жанра даёт ожидаемый URL.
- Парсер найден реестром, `reg.broken()` пуст; все ключи каталога есть в `ru` и
  `en`; у каждой колонки и настройки есть `title_key`.
- README парсера добавлен в пары `tests/unit/test_readme_translations.py`.

Живая проверка — прогон сайта в `uwp-worker` на `all-genres` и на `electronic`:
от 1 до 50 строк (`hip-hop` отдавал 49, поэтому «ровно 50» не утверждаем),
`published` заполнена, `duration` вида `2:17`.

## 8. Документация

- `src/uwp/parsers/soundcloud_trending/README.md` + `README.ru.md` — как у
  `steam_deals`: источник, hydration и перехват, настройки, колонки, почему
  счётчики волатильны, почему нет запасного DOM-пути, как обновить фикстуру,
  что смена жанра пересобирает набор строк.
- `docs/README.md` / `docs/README.ru.md` — в разделе «Writing your own parser»
  одна строка о том, что парсеров в репозитории два и SoundCloud показывает
  перехват ответа как приём.

## 9. Риски

- **SoundCloud меняет разметку/внутренний API.** Hydration — серверный блок,
  перехват и `fetch` бьют в один и тот же `/tracks`. Если сломается всё, прогон
  падает `blocked` с `empty.html`, а не врёт отчётом.
- **Геоблок.** В некоторых странах страница отдаёт заглушку; это тот же
  `blocked` с `empty.html`.
- **`client_id` истекает** — вторая попытка может получить 401; тогда `blocked`.
  Ошибка не молчит.
- **50 треков — потолок страницы.** Ограничение сайта, а не парсера.
- **Сборка браузера может снова сломать эту страницу.** Так уже случилось:
  150.0.7871.186 с `--fingerprint` роняет рендерер на `/discover/sets/
  trending-by-genre:*`, поэтому пин стоит на 148.0.7778.215. Смена пина — одна
  константа, но перед ней нужен прогон в контейнере: `blocked` без `empty.html`
  и без строк — это симптом рендерера, а не сети.
