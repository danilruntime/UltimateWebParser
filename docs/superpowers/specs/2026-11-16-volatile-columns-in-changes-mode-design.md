# `changes` mode must not fire on a drifting counter

Дата: 2026-11-16
Статус: на утверждении

## Проблема

Сайт `steam_skidki` стоит в режиме `changes`, но файл приходит почти после
каждого прогона. Измерено на живой базе (`data/uwp.db`):

```
total=70  with_report=63  report&new==0=43
```

Разница между соседними отчётами (`00-45 → 00-49`), по колонкам:

```
added 0  removed 0
{'Отзывов, шт': 11, 'Положительных, %': 1, 'Новое': 1}
```

Метаданные того же файла: `Новых: 0, Изменённых: 11`.

Причина — в цепочке, а не в отправке:

1. `reports.should_export()` при `changes` возвращает `bool(new_keys or changed_keys)`.
2. `runner._save_rows()` строит `changed_keys`, сравнивая **все** колонки парсера
   (`_tracked_view(payload, [col.key for col in parser.columns])`).
3. `steam_deals` отдаёт `review_count` / `review_percent` — живые счётчики,
   которые дрейфуют между двумя прогонами в 4 минуты.
4. Поэтому `changed_keys` практически никогда не пуст, и `changes`
   вырождается в `always`.

Это соответствует букве спеки («сравниваем все поля из `columns` кроме
`collected_at`»), но противоречит смыслу режима: админ просил «только когда
есть что-то новое», а получает файл каждые несколько минут.

## Решение

Парсер сам говорит, какие его колонки описывают *факт*, а какие — *шум*.
`Column` получает флаг `volatile`:

```python
Column("review_count", "Отзывов, шт", 12, volatile=True)
```

`runner._save_rows()` исключает `volatile`-колонки из сравнения: их изменение
не попадает ни в `changed_keys`, ни в подсветку строк, ни в решение
`should_export`.

Колонка по-прежнему попадает в отчёт и в `items.payload`; меняется только
участие в детекции изменений.

Для `steam_deals` волатильными помечаются `review_count` и `review_percent`.
Изменение цены, скидки, платформ, даты выхода и названия продолжает считаться
изменением и присылает файл, даже если новых строк нет.

## Границы

- Режим `always` не меняется: файл пишется всегда.
- Режим `never` не меняется.
- «Новое» (`items.absent`) не меняется.
- Исчезнувшие строки по-прежнему только счётчик в метаданных.
- Никаких миграций: флаг живёт в коде парсера.

## Почему не другие варианты

- **Только `new_keys`** (вариант B) — смена цены без новой строки перестала бы
  присылать файл; молча теряется самое важное для скидочного парсера.
- **Отдельный режим `new_only`** (вариант C) — новый enum, миграция и лишний
  экран в боте ради того же результата; шум от счётчиков остался бы и в
  `changes`.

## Проверка

- Падающий тест: у парсера колонка помечена `volatile`; прогон, где меняется
  только она, не даёт `changed_keys` и не пишет файл в режиме `changes`.
- Парный тест: изменение отслеживаемой колонки по-прежнему даёт файл.
- Тест-пин на `steam_deals`: `review_count` и `review_percent` помечены
  `volatile`.
- Полный `pytest` + `ruff check src tests`; живой прогон в контейнере: два
  прогона подряд в `changes`, файл приходит только если изменилось что-то
  кроме отзывов.
